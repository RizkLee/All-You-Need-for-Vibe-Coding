# 4.5 MongoDB——文档型数据库

> MongoDB 以 JSON 文档的形式存储数据，结构灵活，是 NoSQL 中最流行的选择。

---

## MongoDB 的数据模型

MongoDB 不使用表和行，而是使用**集合（Collection）**和**文档（Document）**：

```
关系型数据库        MongoDB
表（Table）     →  集合（Collection）
行（Row）        →  文档（Document）
列（Column）     →  字段（Field）
主键             →  _id
```

一条 MongoDB 文档：
```json
{
  "_id": "ObjectId('...')",
  "name": "张三",
  "email": "zhang@example.com",
  "profile": {
    "age": 25,
    "city": "北京"
  },
  "tags": ["前端", "全栈"],
  "orders": [
    { "productId": "p001", "amount": 299 },
    { "productId": "p002", "amount": 89 }
  ]
}
```

注意：用户的订单信息可以直接**嵌入**到用户文档里，不需要单独的订单表和 JOIN 操作。这在查询"某个用户和他的订单"时非常高效。

---

## MongoDB 与关系型数据库的思维差异

这是初学者最容易困惑的地方：数据建模的思路完全不同。

**关系型思维（规范化）**：
```
把数据拆分到不同表，减少冗余，通过 JOIN 查询

用户表 + 订单表 + 商品表
查询用户订单：SELECT ... FROM orders JOIN users ON ...
```

**MongoDB 思维（以查询模式为中心）**：
```
思考"最常见的查询是什么"，然后按照查询需求组织文档

如果经常"查询用户及其订单"→ 把订单嵌入用户文档
如果订单需要单独查询/更新 → 独立存储，用引用关联
```

没有对错，只有适合不适合。

---

## MongoDB 的真正优势

**1. 模式灵活性**  
同一个集合里的文档可以有不同的字段。适合：
- 产品属性差异很大（手机有"存储容量"，衣服有"尺码"）
- 快速迭代的应用（随时增加新字段，不需要 ALTER TABLE）
- 用户自定义内容

**2. 水平扩展**  
MongoDB 从设计之初就考虑了分片（Sharding）——把数据分散到多台服务器，这在 MySQL/PostgreSQL 中配置起来更复杂。

**3. 地理位置查询**  
内置 2dsphere 索引，支持"附近的商家"这类地理查询。

---

## MongoDB 的局限

**不支持多文档 ACID 事务（早期）**：  
MongoDB 4.0 后已经支持多文档事务，但性能开销相比单文档操作大。这是它长期被诟病的点。

**JOIN 能力弱**：  
MongoDB 的 `$lookup` 可以做类似 JOIN 的操作，但性能和灵活性远不如 SQL JOIN。如果你的数据有大量关联查询需求，关系型数据库更合适。

**数据一致性**：  
灵活的 Schema 是双刃剑——同一字段可能在不同文档里有不同的数据类型，容易出现脏数据。

---

## MongoDB 适合什么场景

| 适合 | 不适合 |
|------|--------|
| 内容管理（博客、CMS）| 金融交易、账务系统 |
| 用户行为日志存储 | 复杂关联查询 |
| 产品目录（属性差异大）| 需要严格数据一致性 |
| 实时分析（日志聚合）| 强事务场景 |
| 快速原型开发 | 报表和 BI 系统 |

---

## Mongoose：Node.js 的 MongoDB ODM

在 Node.js 项目中，通常用 **Mongoose** 来操作 MongoDB。Mongoose 提供了 Schema 定义（给 MongoDB 加上一些结构约束）、数据验证、模型等功能——类似于关系型数据库的 ORM。

---

## 现实中 MongoDB 的使用现状

MongoDB 在 2010 年代非常流行，有一段时间几乎成了"创业公司的标配"。但随着 PostgreSQL 支持 JSONB、关系型数据库功能不断增强，以及对"什么时候该用 NoSQL"理解的深入，很多场景正在回归关系型数据库。

**实际建议**：如果你的数据本质上是有关联的结构化数据，从 PostgreSQL 开始，更不容易走弯路。MongoDB 在真正需要它特性的场景下再引入。
