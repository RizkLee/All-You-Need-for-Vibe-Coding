# 4.1 数据库概览：关系型与非关系型

> 数据库是持久化存储数据的地方。不同类型的数据库有不同的组织数据的方式，适合不同的场景。

---

## 为什么需要数据库

程序运行时，数据存在内存（RAM）中，程序一关闭，数据就消失了。数据库提供**持久化存储**，让数据在程序关闭后仍然保留。

你也可以把数据存在文件里——但当数据量大、需要快速查找、多用户并发读写时，文件系统远不够用。数据库在这些方面做了大量优化。

---

## 关系型数据库（SQL）

关系型数据库把数据组织成**表（Table）**，表里有**行（Row，记录）**和**列（Column，字段）**，表与表之间可以建立关联。

一个"用户表"的例子：

| id | name | email | created_at |
|----|------|-------|------------|
| 1 | 张三 | zhang@example.com | 2024-01-10 |
| 2 | 李四 | li@example.com | 2024-01-11 |

一个"订单表"：

| id | user_id | total | status |
|----|---------|-------|--------|
| 101 | 1 | 299.00 | paid |
| 102 | 1 | 89.00 | pending |

`orders.user_id` 引用 `users.id`，这就是**关联**（外键）。通过 SQL 查询可以把两张表的数据"连接"起来，查询"张三的所有订单"。

**关系型数据库的特点**：
- **结构固定**：建表时必须定义每列的名字和数据类型（Schema）
- **ACID 事务**：原子性、一致性、隔离性、持久性——保证数据操作的可靠性
- **SQL 语言**：统一的查询语言，有标准，换数据库学习成本低
- **适合**：有明确结构的业务数据（用户、订单、商品、文章）

主流产品：PostgreSQL、MySQL、SQLite、Oracle、SQL Server

---

## 非关系型数据库（NoSQL）

**NoSQL**（Not Only SQL）是一类数据库的统称，它们以不同于表格的方式存储数据，牺牲了一些 SQL 的约束，换来了更大的灵活性或特定场景的性能优势。

NoSQL 有几个主要分支：

### 文档型（Document）

数据以**文档**（类似 JSON）的形式存储，每个文档可以有不同的字段：

```json
{
  "_id": "user_001",
  "name": "张三",
  "email": "zhang@example.com",
  "addresses": [
    { "city": "北京", "street": "朝阳区XX路" },
    { "city": "上海", "street": "浦东新区XX路" }
  ],
  "preferences": { "theme": "dark", "language": "zh" }
}
```

同一个集合里的文档不需要有相同的结构，非常灵活。代表：**MongoDB**

### 键值型（Key-Value）

最简单的存储模型：`key → value`，极快。代表：**Redis**

```
"user:1:name" → "张三"
"session:abc123" → {"userId": 1, "expiry": "..."}
"product:views:100" → 9527
```

### 列族型（Column-Family）

适合大量写入、海量数据的场景。代表：Cassandra、HBase

### 图型（Graph）

以节点和边来存储数据，特别适合关系网络。代表：Neo4j

```
(张三) -[好友]→ (李四) -[好友]→ (王五)
(张三) -[购买]→ (商品A)
```

---

## 关系型 vs 非关系型：怎么选

这是最常见的困惑，用一个判断框架来思考：

```
你的数据有固定、可预测的结构吗？
  是 → 关系型（PostgreSQL / MySQL）

数据之间有大量关联关系需要查询？
  是 → 关系型

需要强一致性（如金融交易）？
  是 → 必须用关系型，有 ACID 事务保证

数据结构灵活多变、字段不固定？
  → 文档型（MongoDB）

需要极高速的读写、缓存？
  → Redis

数据量极大（TB/PB），查询模式简单？
  → 列族型（Cassandra）

数据是关系网络（社交关系、推荐系统）？
  → 图型（Neo4j）
```

**实际项目中**，最常见的组合是：**PostgreSQL（主数据库）+ Redis（缓存）**。

## ACID 事务是什么

事务是一组操作，要么全部成功，要么全部失败。

经典例子——银行转账：

```
张三 → 李四 转 100 元

步骤：
  1. 张三账户 -100
  2. 李四账户 +100

如果步骤 1 成功，步骤 2 失败（系统崩溃）→ 钱就消失了！

有了事务（ACID）：
  步骤 2 失败 → 步骤 1 自动回滚 → 两者都恢复原状
```

- **原子性（A）**：操作要么全部完成，要么全部撤销
- **一致性（C）**：操作前后，数据库始终处于合法状态
- **隔离性（I）**：并发的事务互不干扰
- **持久性（D）**：提交的数据永久保存，即使系统崩溃

---

## CAP 理论（了解即可）

分布式数据库设计中有一个著名的 CAP 理论：

- **C（Consistency）一致性**：所有节点看到的数据相同
- **A（Availability）可用性**：每个请求都能得到响应
- **P（Partition Tolerance）分区容错性**：网络分区时系统仍能工作

三者只能同时满足两个。这解释了为什么 MongoDB 和 Redis 在极高并发下可能出现短暂的数据不一致，但性能极好。
