# 8.3 前后端分离 vs 全栈框架

> 这是现代 Web 开发中最常见的架构决策之一，没有绝对的好坏，只有适合与否。

---

## 两种模式的本质

**前后端分离**：
```
前端项目 (React SPA)          后端项目 (Express/FastAPI)
    运行在 Vercel         ←→      运行在 Railway/ECS
    localhost:3000               localhost:8000
         ↕ API 调用 ↕
```
两个独立项目，独立部署，通过 HTTP API 通信。

**全栈框架（以 Next.js 为例）**：
```
统一项目 (Next.js)
    前端页面（React）          → 运行在浏览器
    API Routes                  → 运行在服务器
         一个项目，一次部署
```
前端和轻量后端在同一代码库，共享类型定义，一次部署。

---

## 前后端分离的优势

**职责清晰**：前端团队和后端团队可以完全独立工作，只需要约定 API 文档。

**技术自由**：前端可以选 React，后端可以选 Python FastAPI，两者互不干扰。

**独立扩展**：前端访问量大，可以单独扩展 CDN；后端计算压力大，可以单独加服务器实例。

**适合大型团队**：当前端团队和后端团队各自有十几人时，各自维护独立仓库更合理。

**后端可服务多个客户端**：同一套 API，可以同时为 Web 前端、iOS App、Android App、第三方服务使用。

---

## 全栈框架（Next.js）的优势

**一个代码库，减少协调成本**：前后端代码在同一个仓库，类型定义共享，改 API 时前后端可以同步修改。

**类型安全的端到端体验**：用 tRPC（TypeScript RPC 库）可以实现从数据库到前端的完整类型推断，API 接口改了，前端编译时就能发现。

**更简单的部署**：一次 git push，Vercel 搞定一切，不需要管理两套 CI/CD。

**更适合小团队和个人开发者**：一个人可以轻松维护整个应用，不需要在两个仓库之间切换。

**Server Components 直接读取数据库**：Next.js App Router 的 Server Component 可以直接查询数据库，连 API 请求都省了。

---

## 什么时候用哪种

```
选前后端分离，当：
  ✓ 团队有独立的前端团队和后端团队
  ✓ 后端需要服务多个客户端（Web + App + 第三方）
  ✓ 后端逻辑非常复杂，需要专属后端框架（如 Spring、Django）
  ✓ 前后端技术栈差异大（如 React 前端 + Python 后端）
  ✓ 系统规模大，各层需要独立扩展

选全栈框架（Next.js），当：
  ✓ 小团队或个人开发者
  ✓ Web 是唯一或主要客户端
  ✓ 追求快速上线，减少配置成本
  ✓ 前后端都用 TypeScript，想要端到端类型安全
  ✓ 预算有限，只想用一个部署平台
```

---

## 混合方案：Next.js + 独立后端

很多实际项目采用中间方案：

```
Next.js 应用
  └── 前端页面
  └── API Routes（轻量 BFF：认证、数据聚合）
           ↓ 内部调用
      独立后端服务（复杂业务逻辑、批处理）
           ↓
      数据库 + 消息队列
```

Next.js 处理面向用户的请求，独立后端处理复杂业务逻辑（如异步任务、微服务）。两者结合，兼顾了开发效率和扩展性。

---

## tRPC：全栈类型安全

如果你用 Next.js 全栈方案，**tRPC** 是一个非常值得了解的工具：

传统方式：后端定义 API，前端手动写 fetch/axios，类型需要手动保持同步（容易出错）。

tRPC 方式：在同一个 TypeScript 代码库里定义"过程"（procedure，相当于函数），前端调用这些过程就像调用本地函数一样，类型完全自动推断。

这是 Next.js 全栈开发中端到端类型安全的最佳实践之一。
