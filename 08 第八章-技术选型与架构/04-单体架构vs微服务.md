# 8.4 单体架构 vs 微服务架构

> 这是后端系统设计中的经典话题，理解它能让你对系统规模和复杂度有更清醒的认识。

---

## 单体架构（Monolith）

**单体架构**是最直接的方式：整个应用是一个单一的进程，所有功能都在这一个代码库和一个部署单元里。

```
一个 Express/Django/Spring Boot 应用
  ├── 用户模块
  ├── 订单模块
  ├── 支付模块
  ├── 商品模块
  └── 通知模块
  （共享同一个数据库）
```

**单体的优点**：
- **简单**：一个项目，一次部署，本地开发方便
- **事务一致性**：操作跨越多个模块时，可以用单一数据库事务保证原子性
- **性能**：模块间调用是函数调用，没有网络开销
- **调试方便**：所有日志在一个地方，调用链路清晰

**单体的缺点（当规模增大时）**：
- **代码库膨胀**：几百个工程师在同一个仓库，合并冲突频繁
- **部署风险大**：改了支付模块，整个应用要重新部署，任何模块的 bug 都可能影响所有功能
- **技术栈统一**：所有模块必须用同一种语言/框架
- **扩展粗糙**：用户模块压力大，但整个应用只能一起扩展，浪费资源

---

## 微服务架构（Microservices）

**微服务**把一个大系统拆分成多个独立的小服务，每个服务负责一个业务领域，独立部署、独立扩展、甚至可以用不同技术栈：

```
用户服务    (Node.js + PostgreSQL)    ← 只管用户相关
订单服务    (Java + MySQL)            ← 只管订单相关
支付服务    (Go + PostgreSQL)         ← 只管支付相关
商品服务    (Python + MongoDB)        ← 只管商品相关
通知服务    (Node.js + Redis)         ← 只管推送邮件短信
    ↕           ↕           ↕
         API 网关（对外统一入口）
              ↓
           前端 / App
```

**微服务的优点**：
- **独立部署**：改了支付服务，只重新部署支付服务
- **独立扩展**：商品列表访问量大，单独给商品服务加机器
- **技术自由**：支付服务用 Go 追求高性能，推荐服务用 Python 用机器学习
- **团队边界清晰**：每个团队拥有一个或几个服务

**微服务的代价**：
- **分布式系统的复杂性**：服务间网络调用可能失败，需要重试、熔断、限流
- **事务困难**：跨服务的数据一致性非常难处理（没有单一事务）
- **运维复杂**：几十个服务需要 Kubernetes 编排、服务发现、链路追踪
- **调试困难**：一次请求可能经过 10 个服务，排查问题需要分布式追踪工具

---

## 一个核心观点：别一开始就用微服务

Martin Fowler（微服务的重要推广者）本人也说：

> "几乎所有成功的微服务系统，都是从单体架构开始，随着规模增长逐渐拆分的。"

微服务不是"现代先进"，单体不是"落后"。对于大多数创业公司和中小型项目，**先把单体做好，当痛点真的出现时再拆分**。

**何时考虑微服务**：
- 团队超过 50-100 人，协作产生明显阻碍
- 某个模块的负载远高于其他模块，需要独立扩展
- 不同模块需要不同技术栈（如 AI 推荐模块用 Python）
- 系统需要 7×24 不停机部署

---

## 中间方案：模块化单体（Modular Monolith）

一个好的过渡方案：在单体内部，按业务边界清晰地划分模块，模块间通过接口通信（而不是直接调用），不共享数据库表。

这样当未来需要拆分某个模块成微服务时，改动量最小——只需要把内部接口换成 HTTP API。

---

## 相关概念

**API 网关**：微服务架构中对外暴露的统一入口，负责路由、认证、限流、监控。外部只知道一个地址，内部是多少个服务外部不感知。

**服务发现（Service Discovery）**：微服务的 IP 和端口不是固定的（容器会重启），服务发现系统让服务自动找到彼此（Consul、Kubernetes 内置）。

**消息队列（Message Queue）**：微服务间的异步通信媒介，一个服务把消息发到队列，另一个服务从队列取消息处理，两者解耦。代表：RabbitMQ、Apache Kafka、AWS SQS。
