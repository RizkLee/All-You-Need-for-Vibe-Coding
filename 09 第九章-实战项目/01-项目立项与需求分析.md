# 9.1 项目立项与需求分析

> 本章通过一个完整的实战项目，把前八章的知识串联起来。

## 实战项目：TaskFlow——团队任务管理应用

我们将规划一个类似 Todoist / Linear 的任务管理产品，覆盖从需求分析到上线的完整流程。

**产品定位**：为小团队提供的轻量任务管理工具，支持 Web 访问和移动 App。

---

## 需求分析

### 核心用户故事

首先用"用户故事"描述功能，而不是技术语言：

**用户注册与认证**：
- 作为新用户，我希望用邮箱+密码注册账号
- 作为用户，我希望用 Google 账号快速登录
- 作为用户，我希望在不同设备上保持登录状态

**任务管理**：
- 作为用户，我希望创建任务，包含标题、描述、截止日期、优先级
- 作为用户，我希望把任务分配给团队成员
- 作为用户，我希望把任务组织到"项目"下
- 作为用户，我希望把任务标记为完成
- 作为用户，我希望筛选查看"今天的任务"、"过期任务"

**团队协作**：
- 作为用户，我希望创建团队，邀请成员
- 作为用户，当我的任务有更新时，收到通知

**MVP 范围**（第一版只做核心功能）：
```
✓ 用户注册/登录
✓ 创建/完成/删除任务
✓ 任务有标题、描述、截止日期、优先级
✓ 基本的项目分组
✗ 团队协作（第二版）
✗ 实时通知（第二版）
✗ 移动 App（第二版）
```

## 竞品分析

在开始技术选型前，研究竞品了解行业标准：

| 产品 | 优势 | 劣势 | 我们的差异化 |
|------|------|------|-------------|
| Todoist | 功能完整 | 价格高 | 更适合小团队，免费功能更多 |
| Linear | 工程师友好 | 偏项目管理，不够轻量 | 更简单直接 |
| Notion | 灵活 | 太复杂 | 专注任务，不做笔记 |

## 非功能性需求

这些需求不是"功能"，但同样重要：

**性能**：页面首屏加载 < 2 秒，任务操作响应 < 200ms

**安全**：用户只能看到自己的数据，密码加密存储，HTTPS

**可用性**：目标 99.9% 可用时间（允许每月约 43 分钟不可用）

**可扩展性**：初期设计支持 1000 用户，架构需要能扩展到 10 万用户

**数据合规**：如果面向中国用户，需要考虑 ICP 备案和数据存储合规

## 项目文档规范

在动手写代码之前，建立文档：

```
docs/
  requirements.md       ← 需求文档（本节内容）
  api-spec.md          ← API 接口规范
  database-schema.md   ← 数据库 Schema 设计
  architecture.md      ← 架构决策记录（ADR）
  development.md       ← 本地开发指南
  deployment.md        ← 部署指南
```

**ADR（Architecture Decision Record，架构决策记录）**：记录每一个重要的技术选型决策，包括为什么做这个选择、考虑了哪些替代方案、这个选择的取舍。这对未来的维护和新成员加入非常有价值。
