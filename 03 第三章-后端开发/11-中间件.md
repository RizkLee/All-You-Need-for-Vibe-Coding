# 3.11 中间件的概念与使用

> 中间件是一种设计模式：把横切多个请求的通用逻辑抽出来，形成可复用的处理层。

---

## 为什么需要中间件

假设每个 API 接口都需要：
1. 记录请求日志
2. 验证用户是否登录
3. 检查请求频率

如果把这些逻辑写在每个路由处理函数里，代码会大量重复。**中间件**（Middleware）的思路是：把这些通用处理步骤提取出来，让每个请求都自动经过这些步骤。

---

## 中间件的执行模型

中间件的本质是**请求处理管道**（Pipeline）：

```
HTTP 请求
    │
    ▼
┌─────────────────┐
│  中间件 1：日志  │  记录请求方法、URL、时间
└────────┬────────┘
         │ next()
         ▼
┌─────────────────────┐
│  中间件 2：解析请求体 │  把 JSON 字符串解析为 JS 对象
└────────┬────────────┘
         │ next()
         ▼
┌─────────────────┐
│  中间件 3：认证  │  验证 Token，注入用户信息
└────────┬────────┘
         │ next()
         ▼
┌─────────────────────┐
│  路由处理函数（业务）  │  真正的业务逻辑
└─────────────────────┘
         │
         ▼
    HTTP 响应
```

每个中间件可以：
- 对请求做处理（读取/修改）
- 对响应做处理
- 调用 `next()` 把控制权传给下一个中间件
- 直接结束请求（如认证失败，直接返回 401）

---

## 常见中间件类型

### 日志中间件
记录每个请求的方法、路径、响应时间、状态码。生产环境必备，用于排查问题和分析流量。

常用工具：Morgan（Node.js）、Python 的 uvicorn 日志。

### 请求解析中间件
HTTP 请求体是原始字节流，需要解析才能使用。常见需要解析的格式：
- `application/json` → 解析为对象
- `application/x-www-form-urlencoded` → 解析表单数据
- `multipart/form-data` → 解析文件上传

### CORS 中间件
处理跨域资源共享（Cross-Origin Resource Sharing）。当前端和后端部署在不同域名时，浏览器会阻止跨域请求，CORS 中间件在响应头中添加允许的来源，告诉浏览器这个请求是被允许的。

### 认证中间件
验证请求是否附带有效的 JWT Token 或 Session，并把解析出的用户信息附加到请求对象上，供后续处理函数使用。

### 限流中间件
防止某个 IP 或用户短时间内发送过多请求（暴力破解、DDoS）。如"每分钟最多 60 次请求"，超出则返回 429 状态码。

### 缓存中间件
对某些接口的响应进行缓存（通常用 Redis），相同的请求直接返回缓存结果，减少数据库压力。

### 错误处理中间件
统一捕获处理函数抛出的错误，转换成标准化的错误响应格式，而不是把原始错误信息暴露给用户。

---

## 中间件的作用域

中间件可以作用于不同范围：

```
全局中间件：对所有请求生效
  → 日志、请求解析、CORS

路由级中间件：只对某个路由或路由组生效
  → 认证中间件（只保护需要登录的路由）

内联中间件：只对单个路由生效
  → 特殊权限检查
```

---

## 中间件链的设计哲学

中间件体现了**关注点分离**（Separation of Concerns）原则：

- 业务逻辑函数只处理业务逻辑
- 认证、日志、限流等横切关注点由专门的中间件处理
- 各层之间松耦合，易于增删和调整

这种思路在很多地方都能看到：前端的 Redux 中间件、React 的 HOC（高阶组件）、Vue 的导航守卫、Spring 的 AOP（面向切面编程）——本质都是类似的思路。
