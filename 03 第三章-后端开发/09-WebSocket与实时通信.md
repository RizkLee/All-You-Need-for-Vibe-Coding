# 3.9 WebSocket 与实时通信

> HTTP 是"问一答一"的模式，而 WebSocket 建立了一条持久的双向通道，服务器可以主动推送数据。

---

## HTTP 的局限：拉取 vs 推送

标准 HTTP 通信是**客户端主动拉取**的模式：

```
客户端：有没有新消息？
服务器：没有。

客户端：有没有新消息？
服务器：没有。

客户端：有没有新消息？
服务器：有了，给你。
```

这叫**轮询（Polling）**，很浪费——大部分请求都是无意义的空响应。

对于**实时性要求高**的场景（聊天、股票行情、游戏、协作编辑），我们需要**服务器主动推送**的能力。

---

## WebSocket：持久双向连接

**WebSocket** 是一个协议，它在客户端和服务器之间建立一条持久的**全双工**通道：

```
连接建立（通过 HTTP 握手升级）：
  客户端 → 服务器："我想升级到 WebSocket"
  服务器 → 客户端："OK，连接已建立"
        ↕ （连接保持，双方可以随时互发消息）
  服务器 → 客户端："新消息来了！"
  客户端 → 服务器："我发一条消息"
  服务器 → 客户端："用户 B 在线了"
  ...（直到任意一方关闭连接）
```

WebSocket 的 URL 以 `ws://` 或 `wss://`（加密）开头，而不是 `http://`。

---

## WebSocket 适用的场景

| 场景 | 实时性要求 | 为什么需要 WebSocket |
|------|------------|---------------------|
| 即时聊天（微信、Slack） | 极高 | 消息要毫秒级到达 |
| 实时协作编辑（Notion、Google Docs）| 极高 | 所有人的光标和修改实时同步 |
| 股票/加密货币行情 | 高 | 价格每秒变化，需要推送 |
| 在线多人游戏 | 极高 | 玩家位置实时同步 |
| 实时通知（新邮件、新点赞）| 中 | 用户不需要刷新页面 |
| 直播弹幕 | 高 | 弹幕实时显示 |

---

## 轮询的替代方案对比

在 WebSocket 之前，实现"实时"效果有几种变通方法：

| 方案 | 原理 | 缺点 |
|------|------|------|
| **短轮询** | 每隔几秒请求一次 | 浪费资源，实时性差 |
| **长轮询** | 请求后服务器"挂住"，有数据才返回 | 实现复杂，服务器资源占用高 |
| **SSE（Server-Sent Events）** | 服务器单向推送流 | 只能服务器推客户端，不能反向 |
| **WebSocket** | 全双工持久连接 | 需要额外的服务器支持 |

**SSE** 值得单独说一下：它是基于普通 HTTP 的流式响应，服务器可以持续发送数据给客户端。适合**单向推送**的场景（如 AI 流式输出文字、实时日志）。现在很多 AI 产品（ChatGPT 流式输出）用的就是 SSE，而不是 WebSocket。

---

## Socket.io

**Socket.io** 是对 WebSocket 的封装库，在 Node.js 生态中非常流行。它增加了：
- **自动降级**：如果 WebSocket 不可用，自动回退到长轮询
- **房间（Room）机制**：把连接分组（如聊天室）
- **事件系统**：比裸 WebSocket 更易用的 API
- **重连机制**：断线自动重连

在 Flutter、React Native 等移动端，也有对应的 Socket.io 客户端库。

---

## 实时通信的服务端压力

WebSocket 连接是**持久的**，这意味着服务器需要同时维持大量的长连接。

- 普通 HTTP 服务器：每个请求处理完就释放
- WebSocket 服务器：一万个用户在线 = 一万个持久连接

这对服务器的内存和并发模型有更高要求。Node.js（事件驱动）和 Go（goroutine）在这方面表现很好，都能轻松处理数万个 WebSocket 连接。

大规模的实时系统（如直播平台）通常还需要：
- **消息队列**（如 Redis Pub/Sub）：在多台服务器间广播消息
- **水平扩展**：多台服务器同时处理连接，需要粘性会话（Sticky Session）或共享状态
