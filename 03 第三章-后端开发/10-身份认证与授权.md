# 3.10 身份认证与授权：JWT、OAuth2、Session

> "你是谁"和"你能做什么"是每个 Web 应用都必须解决的两个问题。

---

## 认证（Authentication）vs 授权（Authorization）

这两个概念经常混淆，但有本质区别：

| | 认证（Authentication）| 授权（Authorization）|
|--|---------------------|---------------------|
| 问题 | 你是谁？ | 你能做什么？ |
| 时机 | 登录时 | 每次请求时 |
| 手段 | 密码、Token、人脸 | 权限角色、规则检查 |
| 类比 | 出示身份证 | 凭证件判断你能不能进这个区域 |

---

## Session + Cookie（传统方案）

最经典的认证方式：

```
登录流程：
  1. 用户提交用户名和密码
  2. 服务器验证通过，在服务器内存（或 Redis）中创建一个 Session，
     记录 { sessionId: "abc123", userId: 1, role: "admin" }
  3. 服务器通过 Set-Cookie 把 sessionId 发给浏览器
  4. 之后每次请求，浏览器自动带上 Cookie: sessionId=abc123
  5. 服务器查询 Session 存储，找到用户信息

退出登录：
  服务器删除 Session 记录，Cookie 自然失效
```

**优点**：简单，退出登录立即生效，服务器完全掌控。

**缺点**：
- Session 数据存在服务器端，多台服务器需要共享 Session（通常用 Redis）
- 移动 App 不方便使用 Cookie

## JWT（JSON Web Token）

**JWT** 是一种**无状态**的认证方案：服务器不存储 Session，把用户信息直接编码在 Token 里。

Token 是一个由三部分组成的字符串（用点分隔）：

```
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjEsInJvbGUiOiJ1c2VyIn0.abc123xyz

Header（算法信息）. Payload（载荷，存储用户数据）. Signature（签名）
```

**Payload 里存什么**：
```json
{
  "userId": 1,
  "email": "zhang@example.com",
  "role": "admin",
  "exp": 1735689600  // 过期时间（Unix时间戳）
}
```

**Signature 的作用**：用服务器的密钥对 Header + Payload 签名，确保 Token 没有被篡改。任何人都能解码 Payload（它只是 Base64 编码），但无法伪造 Signature。

**JWT 的工作流**：

```
登录 → 服务器生成 JWT 返回给客户端
       ↓
客户端存储 Token（localStorage 或内存中）
       ↓
每次请求：Authorization: Bearer <jwt_token>
       ↓
服务器验证签名 → 解析 Payload 获取用户信息 → 处理请求
```

**JWT 的优点**：
- 无状态，服务器不需要存储 Session，天然支持水平扩展
- 移动端友好（不依赖 Cookie）
- 可以在多个服务间共享（微服务场景）

**JWT 的缺点**：
- **无法立即吊销**：Token 在过期前始终有效。用户登出，或者 Token 被盗，服务器无法使其失效（除非引入黑名单，那又变成有状态了）
- Token 存在客户端，XSS 攻击可能窃取（存 localStorage 有风险，存 HttpOnly Cookie 更安全）

## OAuth 2.0：第三方登录的标准

你一定用过"用微信登录"、"用 Google 账号登录"——这背后就是 **OAuth 2.0**。

OAuth 2.0 解决的问题：**让用户授权第三方应用访问自己在某平台的数据，而不需要把密码给第三方**。

简化流程：

```
用户点击"用 Google 登录"
  ↓
跳转到 Google 的授权页面
  ↓
用户在 Google 那里登录并确认授权
  ↓
Google 把一个授权码（code）返回给你的应用
  ↓
你的应用服务器用 code 换取 access_token
  ↓
用 access_token 调用 Google API，获取用户信息（邮箱、头像等）
  ↓
在你的系统中创建用户，生成 JWT，完成登录
```

OAuth 2.0 中的角色：

| 角色 | 例子 |
|------|------|
| **资源所有者** | 用户（张三）|
| **客户端应用** | 你开发的 App |
| **授权服务器** | Google、微信、GitHub |
| **资源服务器** | 存储用户数据的服务（通常和授权服务器在一起）|

**OpenID Connect（OIDC）** 是在 OAuth 2.0 之上的扩展，专门用于身份认证（OAuth 2.0 原本是授权协议），增加了 ID Token 的概念。现代第三方登录几乎都同时实现了 OAuth 2.0 + OIDC。

## 密码存储：哈希与加盐

一个关键的安全原则：**永远不要存明文密码**。

```
正确做法：
用户密码: "mypassword123"
  → bcrypt 哈希（+随机盐值）
  → "$2b$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy"
  → 存入数据库

验证时：
  对输入的密码做同样的哈希，与数据库中存的比对
  （bcrypt 可以在不知道盐值的情况下验证）
```

**bcrypt** 是专为密码设计的哈希算法，故意设计得"慢"（可调节），使暴力破解更难。SHA256、MD5 等通用哈希不应用于密码，因为太快，容易被彩虹表攻击。

## 权限控制（Authorization）

常见的权限模型：

**RBAC（基于角色的权限控制）**：
```
用户 → 角色 → 权限
张三 → admin → 可以增删改查所有用户
李四 → editor → 只能修改内容，不能删除用户
王五 → viewer → 只能查看
```

**ABAC（基于属性的权限控制）**：更细粒度，基于用户属性、资源属性、环境条件综合判断。适合复杂的业务场景。

## 常见安全攻击与防御

| 攻击类型 | 原理 | 防御方法 |
|----------|------|----------|
| **XSS** (跨站脚本) | 注入恶意 JS，窃取 Cookie/Token | 转义输出，Content-Security-Policy，HttpOnly Cookie |
| **CSRF** (跨站请求伪造) | 利用用户的 Cookie 发起伪造请求 | SameSite Cookie，CSRF Token |
| **SQL 注入** | 通过输入数据操控 SQL 查询 | 参数化查询，使用 ORM |
| **暴力破解** | 不停尝试密码 | 限流，账号锁定，验证码 |
