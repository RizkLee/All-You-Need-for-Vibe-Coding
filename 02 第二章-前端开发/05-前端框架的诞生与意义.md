# 2.5 前端框架的诞生与意义

> 前端框架解决了什么问题？为什么不直接写 HTML + CSS + JS？

---

## 问题的起点：原生 JS 的困境

假设你要用原生 JS 构建一个任务列表：

```javascript
// 获取数据
const tasks = [
  { id: 1, title: "买菜", done: false },
  { id: 2, title: "写代码", done: true }
]

// 渲染到页面
function renderTasks() {
  const list = document.getElementById('task-list')
  list.innerHTML = tasks.map(task => `
    <li class="${task.done ? 'done' : ''}">
      <input type="checkbox" ${task.done ? 'checked' : ''} 
             onchange="toggleTask(${task.id})">
      ${task.title}
    </li>
  `).join('')
}

// 切换状态
function toggleTask(id) {
  const task = tasks.find(t => t.id === id)
  task.done = !task.done
  renderTasks()  // 重新渲染整个列表！
}
```

这段代码有几个问题：
1. **数据和 UI 不同步**：每次数据变化都要手动调用渲染函数
2. **性能差**：每次都重建整个 DOM，即使只改了一个勾选框
3. **难以维护**：随着功能增加，代码越来越混乱
4. **难以复用**：同样的"任务卡片"如果在多处使用，代码会重复

---

## 框架解决的核心问题

前端框架（React、Vue、Angular）都围绕同一个核心思想：

**声明式渲染（Declarative Rendering）**

```
命令式（原生 JS）：告诉浏览器"怎么做"
"找到列表元素，清空它，遍历数组，创建 li 元素，设置文本，添加到列表..."

声明式（框架）：告诉框架"要什么结果"
"当 tasks 是这个数组时，显示这样的列表"
```

框架负责把声明的结果变成实际的 DOM，你只需要管理数据，框架自动更新 UI。

---

## 组件化（Componentization）

框架让你把 UI 拆分成**可复用的组件**：

```
App（根组件）
├── Header（导航栏组件）
├── TaskList（任务列表组件）
│   ├── TaskItem（单个任务组件）
│   └── TaskItem
└── Footer（底部组件）
```

每个组件：
- 有自己的 HTML 结构、样式和逻辑
- 可以接收外部传入的数据（Props）
- 维护自己的内部状态（State）
- 可以在任何地方复用

---

## 虚拟 DOM（Virtual DOM）

React 等框架引入了**虚拟 DOM** 来提升性能：

```
真实 DOM 操作（慢）：直接修改浏览器中的 DOM 树
虚拟 DOM（快）：在内存中维护一棵 JS 对象树，计算出最小变更，再批量更新真实 DOM
```

流程：
```
数据变化
  → 重新计算虚拟 DOM
  → 与上一次虚拟 DOM 对比（Diff 算法）
  → 只更新真正变化的部分
  → 真实 DOM 最小化更新
```

Vue 3 使用了响应式系统（Proxy），精准追踪哪个数据变了，不需要 Diff 整棵树，性能更优。

## 状态驱动 UI

框架的核心心智模型：

```
UI = f(state)
```

界面是状态的函数。**状态**（State）是数据，界面由状态决定。当状态改变，界面自动更新。

```jsx
// React 示例
function TaskList() {
  const [tasks, setTasks] = useState([
    { id: 1, title: "买菜", done: false }
  ])

  // 只需要更新 state，UI 自动刷新
  const toggleTask = (id) => {
    setTasks(tasks.map(t =>
      t.id === id ? { ...t, done: !t.done } : t
    ))
  }

  return (
    <ul>
      {tasks.map(task => (
        <li key={task.id} onClick={() => toggleTask(task.id)}>
          {task.done ? "✅" : "⬜"} {task.title}
        </li>
      ))}
    </ul>
  )
}
```

## 三大框架的诞生背景

| 框架 | 诞生年份 | 创造者 | 核心理念 |
|------|----------|--------|----------|
| **Angular** | 2010 | Google | 完整框架，约定大于配置，适合企业级 |
| **React** | 2013 | Facebook | UI 库，只管视图层，自由组合 |
| **Vue** | 2014 | 尤雨溪 | 渐进式框架，易上手，中间路线 |

这三个框架都解决了同样的根本问题，但选择了不同的设计哲学：

- **Angular**：全包式，带路由、表单、HTTP、测试工具，适合需要统一规范的大团队
- **React**：只做 UI 层，路由、状态管理自己选，灵活但需要更多配置
- **Vue**：在完整和灵活之间取平衡，官方提供路由和状态管理，但不强制

---

## 框架带来的完整生态

选择一个框架不只是选择了一个库，而是选择了一个**生态系统**：

```
React 生态
├── Next.js（全栈框架）
├── React Router（路由）
├── Redux / Zustand（状态管理）
├── React Query（服务端状态管理）
└── styled-components / shadcn/ui（UI组件库）

Vue 生态
├── Nuxt.js（全栈框架）
├── Vue Router（路由，官方）
├── Pinia（状态管理，官方）
└── Element Plus / Vuetify（UI组件库）
```

---

## 什么时候不需要框架

不是所有项目都需要框架：

- **简单的静态页面**：HTML + CSS + 少量 JS 就够了
- **内容展示为主的网站**：可以考虑静态站点生成器（Hugo、Astro）
- **性能极致优化**：减少 JS 包大小

但对于需要**动态交互、复杂状态、多页面**的 Web 应用，框架几乎是标准选择。
