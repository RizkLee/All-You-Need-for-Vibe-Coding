# 5.1 什么是全栈框架

> 全栈框架把前端和后端整合在一个项目里，解决了前后端分离的配置和协调成本问题。

---

## 前后端分离的痛点

标准的前后端分离方案需要维护两个独立项目：

```
前端项目 (React App)        后端项目 (Express API)
  src/                        src/
  package.json                package.json
  .env                        .env
  部署到 Vercel               部署到 AWS EC2
  运行在 localhost:3000        运行在 localhost:8000
```

这带来了一些问题：
- **两套配置**：两个仓库（或 Monorepo），两个 CI/CD 流程，两个部署目标
- **跨域问题（CORS）**：本地开发时前后端端口不同，需要额外配置
- **类型不同步**：API 返回的数据结构在前后端分别定义，容易出现不一致
- **协调成本**：改 API 接口时要同时修改前端和后端

---

## 全栈框架的核心理念

全栈框架把前端渲染和部分后端逻辑**放在同一个项目**里：

```
全栈项目 (Next.js)
  pages/ 或 app/
    page.tsx              ← 前端页面
    api/
      users/route.ts      ← 后端 API（运行在服务器上）
  package.json
  部署到 Vercel           ← 前后端一起部署
```

前端代码和 API 代码共用同一套语言（TypeScript）、同一套类型定义、同一个部署流程。

---

## 全栈框架能做什么，不能做什么

**能做**：
- 提供 API 接口（类似 Express）
- 服务端渲染（SSR）
- 静态页面生成（SSG）
- 处理认证、数据库查询
- 文件上传、Webhook 处理

**不能替代**：
- 独立的后端服务（处理 WebSocket、定时任务、复杂业务逻辑）
- 专用数据库服务
- 消息队列、缓存服务

全栈框架的 API 层通常是**轻量的 BFF（Backend for Frontend）**，适合中小型应用。对于需要复杂后端逻辑的大型系统，通常还是需要独立的后端服务，全栈框架只承担前端 + 轻量 API 的部分。

---

## 服务端渲染（SSR）vs 客户端渲染（CSR）vs 静态生成（SSG）

全栈框架的核心能力之一是支持多种渲染策略，这是选择全栈框架的重要原因之一：

| 策略 | 缩写 | 页面 HTML 何时生成 | 优势 | 劣势 |
|------|------|-------------------|------|------|
| 客户端渲染 | CSR | 浏览器运行 JS 后 | 交互流畅，纯前端 | SEO 差，首屏慢 |
| 服务端渲染 | SSR | 每次请求时在服务器生成 | SEO 好，首屏快 | 服务器压力大 |
| 静态生成 | SSG | 构建时预先生成 | 极快，可 CDN 缓存 | 内容不能实时更新 |
| 增量静态再生 | ISR | 构建时 + 定时重新生成 | 结合了 SSG 和 SSR 优点 | 配置复杂 |

为什么 SEO 需要 SSR/SSG？  
搜索引擎爬虫不擅长执行 JavaScript，CSR 的页面爬虫看到的可能是空 HTML。SSR 把完整内容直接包含在 HTML 里，爬虫能直接读取。
